# 已采纳 Review 反馈学习

Review 标准学习的是经过验证的判断，不是 reviewer 原话。每条被采纳的 Review 意见都进入候选分析；只有稳定、通用、可执行的结论才能成为正式项目规则。

## 何时认定为已采纳

同时满足以下条件才形成强证据：

- 作者回复、commit message 或 review thread 明确关联到该意见；如果没有显式关联，修改必须足够单一、紧邻评论且只能合理解释为对该意见的响应。
- Review 评论后出现了语义相关的代码或测试修改。
- thread 由 reviewer 确认解决，或 reviewer 在修改后重新 approve；仅由作者自行 resolve 是弱证据。
- 相关修改在后续 commit 中没有被撤回。
- PR 已合入，或已达到除等待合入外的全部条件。

仅有“PR 最终合入”、相邻代码碰巧改变、作者口头回复或对整批修改的 re-approval，不足以断言某条意见被采纳。只有时间和语义相关、但因果无法确认时标记为 `observed-unproven`，不增加规则命中次数；普通只读 Review 停止推广即可，用户正在维护标准时再向用户确认或等待更强证据。

## 学习流水线

`observed → candidate → active → automated / deprecated`

1. 保存 PR、review thread、评论时 head、修改后 head 和 before/after diff 作为证据索引。
2. 提炼失败模式、期望不变量、适用条件、检查动作、验证证据和允许例外。
3. 搜索已有规则并选择候选动作。
4. 对新规则或实质修订做独立、只读交叉审阅。
5. 将正式规则写入最窄的领域文件；GitHub PR/Issue 保存来源历史，规则正文只描述现状。
6. 规则能够确定性检测且误报可控时，再实现 CI 门禁。

## 候选动作

| 动作 | 使用条件 | 结果 |
| --- | --- | --- |
| `reinforce` | 现有规则已经完整覆盖 | 不重复写规则；补足缺失示例或验证方式才改文档 |
| `amend` | 现有规则方向正确，但触发范围、例外或验证不完整 | 最小修改原规则 |
| `new` | 出现新的通用不变量 | 新增稳定 ID 的规则 |
| `one-off` | 只属于当前实现、临时兼容或个人偏好 | 不进入项目标准 |
| `conflict` | 与现有规则或另一个已采纳判断矛盾 | 暂停升级，向用户确认取舍并做 Policy Conflict Review |

## 升级标准

候选必须同时满足：

- **通用**：未来同类改动仍然适用，而不是复述本次 diff。
- **可执行**：Reviewer 能明确知道何时检查、检查什么。
- **可验证**：能描述所需证据或失败信号。
- **有边界**：写清适用范围、例外和不适用场景。
- **无冲突**：已检查核心规则、领域规则和最近的 `AGENTS.md`。

普通低影响候选第一次出现时写入 `review/candidates/`，在第二个独立 PR 或独立根因再次命中后再升级，即总共两次合格命中，不是首次加两次重复。`observed-unproven` 不计数。安全、数据、权限、发布产物、核心兼容性等高影响候选可以一次升级。用户明确表示“以后都应这样”或要求沉淀为项目标准时，可在完成去重、边界确认和交叉审阅后直接升级。具体 ID、贡献、例外和清理规则见 [规则治理](./governance.md)。

## 不明确时向用户确认

以下情况不得自行推广为规则：

- 无法判断被采纳的是通用原则还是当前 PR 的折中。
- 同一修改同时响应多条评论，因果关系不清。
- 用户的意见可能表达产品偏好，而不是工程不变量。
- 新候选会改变既有架构、兼容性或发布政策。
- 规则的适用范围、阻塞级别或例外不清楚。

因果关系不明确时采用这个结构：

> `<意见>` 之后出现了可能相关的 `<修改>`，但现有证据不足以确认这是对该意见的采纳。它是否是在响应这条意见？如果是，我建议将其抽象为 `<候选规则>`，适用于 `<范围>`；这是通用项目约束，还是仅限本 PR 的取舍？

Learning Question 不改变已经成立的 Code Review Verdict。普通只读 Review 可以把证据不足的经验标记为 `observed-unproven` / deferred 并停止推广，Experience Review 仍可 PASS，不要求先获得规则写入授权。用户正在维护标准时再登记候选或请求确认；如果问题同时暴露出现行规则冲突或未解决代码风险，再影响合入结论。

## 正式规则格式

```md
## <DOMAIN>-NNN <规则标题>

Owner：<维护团队或角色>。

适用条件：<什么改动触发检查>。

必须：<需要保持的不变量>。

禁止：<容易导致失败的做法>。

验证：<证据或失败信号>。

默认级别：<P0-P3 或非阻塞验证缺口>。

例外：<允许例外及所需证据>。
```

规则格式还要记录维护团队或角色 Owner。规则 ID 前缀按领域使用 `CORE`、`REVIEW`、`FRONTEND`、`BACKEND`、`DESKTOP`、`RUNTIME`、`CONFIG`、`RELEASE`。不要在正式规则里记录个人身份、聊天原文或过程叙事。

## 写入位置

- 跨领域 Review 不变量：`.oo/rules/review/core-rules.md`。
- 领域行为和验证要求：`.oo/rules/review/profiles/<domain>.md`。
- 模块归属和继续阅读入口：最近的 `AGENTS.md`。
- 常见故障的症状与排查：`.oo/rules/maintenance/common-issues.md`。
- 用户可见的使用变化：`.oo/docs/` 或对应模块 README；不要写进内部 Review 规则。
