# Review 规则治理

任何 contributor 都可以从真实 PR、事故或验证缺口提出规则候选。正式规则保持少而强：可执行、可验证、有适用边界，并且能改变 Review 决策。

## 内容分层

| 内容                   | 位置                     | 生命周期                                  |
| ---------------------- | ------------------------ | ----------------------------------------- |
| Review 入口和硬约束    | `.oo/rules/REVIEW.md`    | 稳定、短小，避免频繁变化                  |
| 跨领域规则             | `review/core-rules.md`   | 对所有 PR 生效                            |
| 领域规则               | `review/profiles/*.md`   | 按 changed paths 和语义加载               |
| 尚未达到升级条件的经验 | `review/candidates/*.md` | 当前候选；升级、判定 one-off 或失效后删除 |
| 可确定性检查           | CI、tests、scripts       | 由规则链接到实现，不重复描述语义          |

## 规则变更 PR

新增或实质修改规则时必须说明：

- 触发它的失败模式或已采纳 Review 证据。
- 与现有规则的搜索和 `reinforce` / `amend` / `new` / `conflict` 判断。
- 适用范围、不适用范围、默认优先级和验证证据。
- 是否适合自动化，以及不自动化的原因。
- 受影响的 profile、模块和例外。

跨领域核心规则需要独立 reviewer PASS。领域规则需要对应模块维护者或熟悉该领域的独立 reviewer PASS。实质改变产品、架构、兼容或发布政策时，先得到用户确认；Reviewer 不能用规则维护流程替代产品决策。

## 稳定 ID

- 正式规则使用 `<DOMAIN>-NNN`，候选使用 `CANDIDATE-<DOMAIN>-NNN`。
- 只有默认分支或用户明确指定基线中的规则是 `active`；当前 PR/worktree 新增的规则是 `proposed`。分类时以 active 基线判断 `new` / `amend` / `reinforce`，同时检查 proposed diff 避免在同一批改动中重复定义。
- 已分配 ID 不改义、不复用。规则范围实质改变时新增 ID，并更新所有引用。
- 纯措辞或验证补充保留原 ID。
- 删除过时规则前先移除调用方、模板和 CI 引用；Git 历史保存来源，不在正文维护迁移叙事。

## 候选登记

普通低影响经验第一次出现时写入 `review/candidates/<id>.md`。候选只保留当前判断和最小证据索引，不复制聊天全文或完整 diff；不得记录个人隐私、凭据或无关身份信息。

候选至少包含：维护团队或角色 Owner、创建/最近审阅/最晚复查日期、失败模式、候选不变量、适用范围、验证方式、已知例外、证据 PR/thread、合格命中次数、待确认问题和建议动作。第二个独立 PR 或独立根因命中后重新去重并考虑升级；`observed-unproven` 不计数。高影响候选或用户明确要求的稳定约束可以一次升级。

证据链接的可见性不得高于当前仓库：公开仓库只能提交公开证据；私有 PR、thread 或事故记录保留在同等权限的私有 tracker，仓库候选中只保存无敏感信息的摘要或内部引用标识。不要把临时签名 URL、token 化链接或本机路径作为长期证据。

候选变为 `reinforce`、`one-off`、正式规则或失效后删除候选文件。Git 和关联 PR 保存历史；候选目录只表示当前未决状态。

## 例外与冲突

- PR 需要违反正式规则时，在 `Review Scope` 中列出规则 ID、原因、影响范围、owner、到期条件或 follow-up。
- P0/P1 规则不能仅凭作者声明豁免；必须由有权决定该产品/架构范围的用户明确确认。
- 两条规则冲突时停止套用冲突部分，形成 `conflict` 候选，列出各自适用场景并请求决策；不得静默选择较新的规则。
- 一次性例外不自动降低规则级别；重复例外说明规则边界可能错误，应发起修订 Review。

## 定期维护

每个发布周期或规则目录明显膨胀时执行一次只读审计：

- 合并重复规则，删除不能改变 Review 结论的空泛表述。
- 检查长期无命中、高例外率或已经被架构淘汰的规则。
- 检查规则与 CI、PR 模板、skill 和模块 `AGENTS.md` 是否冲突。
- 检查候选是否已有第二次命中、已经失效或缺少 owner。

不以评论数、规则数或 Finding 数评价 Reviewer。关注漏出缺陷、规则命中、例外原因、误报和 Review 延迟，避免为了指标制造意见。
